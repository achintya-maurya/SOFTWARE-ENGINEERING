\section{Background and Context}

Municipal services receive reports about damaged roads, waste accumulation, drainage, water supply, street lighting, and other public infrastructure. A report can pass through several people before it is resolved: a resident describes the issue, an officer checks and routes it, and a field worker carries out the work. When these steps are recorded across separate channels, residents may not know whether a report was received, while staff may lack a shared view of its progress.

The Smart City Civic Complaint and Management System is a web application intended to make this process traceable. A resident creates a complaint with a category, title, description, department, and location. The application assigns a database identifier and records the initial status. A department officer reviews the report and can verify or reject it. A verified complaint can be assigned to a worker, who accepts the task, records progress, and uploads completion evidence. The resident can then confirm the reported resolution and leave feedback.

The repository contains a React and Vite frontend, a Python FastAPI service, SQLAlchemy data models, and a PostgreSQL database connection layer. The interfaces and API endpoints cover the principal citizen, officer, and worker workflows. The project also contains an administrator dashboard in the frontend and data models for notifications and service-level escalations; the current backend does not expose a complete administrator-management API or notification/SLA processing workflow. Automated classification, duplicate detection, and priority scoring remain proposed enhancements.

\subsection{Problem Statement}

The project addresses the need for one consistent record of a civic complaint from submission through staff action to resident verification. The system must associate each report with a resident, category, department, current state, and status history, while restricting actions according to user role. It must support a practical staff workflow without representing unimplemented smart features as completed functionality.

\section{Project Objectives}

The project objectives are to:
\begin{enumerate}
\item Provide a web interface for citizen registration, sign-in, complaint creation, and complaint tracking.
\item Implement role-specific sign-in and access checks for citizens, officers, and field workers.
\item Support officer review, verification or rejection, and assignment of a complaint to a department worker.
\item Support task acceptance, work progress updates, notes, completion evidence, and task completion.
\item Record complaint state changes and support citizen resolution verification and feedback.
\item Persist core entities in PostgreSQL through SQLAlchemy models and expose the workflows through REST-style FastAPI endpoints.
\item Evaluate the delivered system against its implemented workflow and document limitations and future work.
\end{enumerate}

\section{System Architecture}

The implementation uses a browser-based client and a server-side API. React renders role-specific pages and sends HTTP requests to FastAPI. The API validates request data, checks the bearer token and role, uses SQLAlchemy sessions to read or update records, and stores persistent application data in PostgreSQL. Complaint photographs are saved in the backend upload directory, with metadata recorded in the evidence table.

\subsection{High-Level Design}

The system is divided into these layers:
\begin{enumerate}
\item \textbf{Presentation layer:} React pages for account access and citizen, officer, worker, and administrator views. Protected routes restrict the citizen, officer, and worker pages by the signed-in role.
\item \textbf{API layer:} FastAPI routes implement registration, sign-in, complaint operations, staff actions, evidence access, and resolution/feedback operations. Pydantic schemas validate request fields.
\item \textbf{Application and access-control layer:} Route handlers enforce ownership and department boundaries, validate allowed transitions, and coordinate database writes.
\item \textbf{Persistence layer:} SQLAlchemy maps Python classes to PostgreSQL tables. Foreign keys, uniqueness rules, and check constraints preserve core relationships and valid status or rating ranges.
\item \textbf{Evidence storage:} Uploaded image files are stored on the backend filesystem; rows in \texttt{complaint\_evidence} associate a file path, uploader, type, and time with a complaint.
\end{enumerate}

The main operational flow is:
\begin{center}\small
Citizen submission $\rightarrow$ Officer review $\rightarrow$ Worker assignment
$\rightarrow$ Work and evidence $\rightarrow$ Citizen verification $\rightarrow$ Resolution
\end{center}

\subsection{Data Model}

The SQLAlchemy models define ten tables. The central complaint row references its citizen, category, and department. Related tables record assignments, status transitions, and evidence. Additional tables represent feedback, notifications, and SLA escalations; the presence of a model alone does not mean a related application workflow is exposed or active.

\begin{longtable}{p{0.24\textwidth}p{0.68\textwidth}}
\toprule
\textbf{Table} & \textbf{Purpose and constraints represented in the model} \\
\midrule
\texttt{users} & Identity, unique email, password hash, role, and optional department. Officer/worker roles require a department. \\
\texttt{departments} & Department name and description. \\
\texttt{categories} & Unique complaint category names and descriptions. \\
\texttt{complaints} & Citizen, category, department, title, description, location, status, and timestamps. Status is constrained to the declared lifecycle values. \\
\texttt{assignments} & Worker assignment, assigning officer, assignment dates, status, progress from 0 to 100, and work notes. \\
\texttt{status\_history} & Actor, prior and new status, remarks, and timestamp for an auditable transition history. \\
\texttt{complaint\_evidence} & Complaint, uploader, media type, stored path, and upload time. \\
\texttt{feedback} & Citizen rating and comments; rating is constrained to 1--5 and each resolution cycle has a unique feedback record. \\
\texttt{notifications} & Notification message, recipient, optional complaint, read flag, and time. \\
\texttt{sla\_escalations} & Escalation level, reason, status, and time for a future or separately operated SLA workflow. \\
\bottomrule
\end{longtable}

\section{Implementation Details}

\subsection{Module 1: Core Functionality}

\subsubsection{Authentication and Role Checks}

Citizens can register through \texttt{/api/auth/register}; the request schema requires a name, email, and password of at least eight characters. Citizen, officer, and worker sign-in use separate routes. The service hashes passwords using \texttt{pwdlib}, issues a signed JWT containing the user identifier, role, and expiry, and expects a bearer token for protected routes. Role checks and ownership filters are applied in route handlers. The frontend stores the token and user summary in \texttt{sessionStorage} and uses role-aware protected routes.

\subsubsection{Complaint Creation and Tracking}

An authenticated citizen submits a category, department, title, description, and location. The backend checks that the category and department exist, creates a complaint with status \emph{Pending Verification}, and writes the initial status-history row in the same database operation. Citizens can list their own complaints, retrieve complaint details, and retrieve chronological status history. Complaint list queries join the category and department names for display.

\subsubsection{Officer Review and Assignment}

The officer API filters complaints to the officer's department. A complaint can be verified or rejected while it is pending verification. Assignment creates an assignment record and moves the complaint to \emph{Assigned}; the officer API also exposes workers for the officer's department. This keeps department scoping in the backend rather than relying only on the frontend.

\subsubsection{Field Work and Resolution}

Workers can retrieve assigned tasks, accept them, start work, save progress, and complete the assignment. The assignment model constrains progress to the range 0--100. Completion marks the complaint \emph{Completed}. A separate citizen action verifies completed work and moves the complaint to \emph{Resolved}. The API also accepts feedback and derives a resolution-cycle number from the complaint's resolution history.

\subsubsection{Evidence Handling}

Citizens can upload complaint photographs and workers can upload completion photographs. The backend checks role and complaint or assignment access before accepting files, writes the file to the evidence directory, and records metadata in the database. Worker completion evidence is limited to three photographs per complaint. Evidence listing and file retrieval routes apply access checks so a user cannot use a public file URL to bypass complaint permissions.

\subsubsection{Implemented Status Flow}

The principal status path supported by the database and API is:
\begin{center}\small
Pending Verification $\rightarrow$ Verified $\rightarrow$ Assigned $\rightarrow$
Accepted $\rightarrow$ In Progress $\rightarrow$ Completed $\rightarrow$ Resolved
\end{center}
A pending complaint can also be rejected. The model permits a \emph{Reopened} state, and the frontend contains a reopened-state display; a complete citizen reopen API is not present in the listed backend routes. The report therefore treats reopening as a represented state, not a fully delivered end-to-end operation.

\subsubsection{Frontend Screens}

The project includes login and registration, citizen dashboard, complaint submission, complaint list and details, officer dashboard and review, worker dashboard and task details, and an administrator dashboard. The report's screenshot set documents the login and primary dashboard/detail interfaces. The citizen, officer, and worker views call backend APIs. The administrator dashboard currently does not have a corresponding API integration in the backend.

\subsection{Module 2: Secondary Features and Supporting Data}

The implementation includes supporting behavior beyond the central status transitions: complaint evidence upload and protected retrieval, chronological status history, worker progress and notes, resident feedback with a resolution-cycle key, and initial health routes. The database also defines notification and SLA escalation entities, but the repository does not contain corresponding operational routes or a scheduler that processes those records. Similarly, automated complaint classification, duplicate detection, priority scoring, maps, and hotspot analytics appear in planning/design material and remain future work.

\section{Testing Methodology}

The repository includes two small Python verification scripts: one checks database connectivity, and one reports the SQLAlchemy model tables. These scripts do not constitute an automated API test suite. The individual project journals record browser checks of the frontend flows and interface states during development. This evaluation combines those project records with a source-level inspection of routes, schemas, models, and frontend integration. No load test, response-time measurement, controlled user study, or independent end-to-end test run is claimed in this report.

The evaluation categories are:
\begin{itemize}
\item \textbf{Component review:} inspect the registration, login, role-aware page routing, complaint forms, and dashboards.
\item \textbf{Integration review:} trace frontend requests to corresponding API routes and data models for citizen, officer, and worker operations.
\item \textbf{Workflow review:} compare the intended status path with the status changes in the backend handlers and schema constraints.
\item \textbf{Persistence and access review:} inspect database foreign keys, ownership/department filters, evidence access checks, and status history writes.
\end{itemize}

\section{Analysis}

The core workflow is represented across user interfaces, API routes, and relational models, which is a stronger implementation state than the earlier report draft described. Status history, department-scoped officer queries, citizen ownership checks, worker assignment, evidence metadata, and completion verification give the complaint lifecycle traceability. The database constraints also prevent several invalid values, including unknown roles, unsupported complaint statuses, progress outside 0--100, and ratings outside 1--5.

The evidence supports the project objectives of providing a connected complaint workflow and persistent data model. Some objectives are only partly met: administrator pages are not backed by a complete administrator API; the schema's notification and SLA concepts do not have active processing flows; reopening is represented but lacks a complete backend action; and smart assistance remains a future extension. Because this report did not execute a benchmark or full end-to-end suite, it makes no claim about production readiness, measured performance, or defect-free behavior.

\section{Summary of Work}

The project delivers a web-based civic complaint workflow with a React frontend, FastAPI backend, SQLAlchemy models, and PostgreSQL persistence. Citizens can register and sign in, submit and track complaints, and review status history. Officers can review complaints within their department, verify or reject them, and assign workers. Workers can accept assigned tasks, update progress and notes, submit completion photographs, and complete the work. Citizens can verify completed work and provide feedback. The design diagrams and project journals document the analysis, modelling, planning, and implementation stages.

\section{Key Findings}

\begin{itemize}
\item A shared complaint identifier and status-history record provide a basis for lifecycle traceability.
\item Role and ownership checks are performed by the API, while protected routes provide a corresponding frontend navigation boundary.
\item A normalized relational model connects users, departments, categories, complaints, assignments, evidence, and feedback.
\item The repository has meaningful implementation beyond a visual prototype, but a few dashboard and schema concepts are not complete operational features.
\item Functional automation and measured non-functional evaluation are the main evidence gaps in the current submission.
\end{itemize}

\section{Future Work and Recommendations}

\begin{enumerate}
\item Add automated unit and integration tests for request validation, role boundaries, status transitions, evidence uploads, and rollback/error paths.
\item Complete administrator APIs and connect the dashboard to persisted, permission-checked data.
\item Implement notification delivery, reopening, and SLA escalation as explicit workflows with documented transition rules.
\item Move uploaded evidence to managed durable storage and add backup, size limits, retention, and deployment configuration.
\item Add observability and conduct measured load, latency, and usability evaluations with documented datasets and procedures.
\item Consider duplicate detection, category suggestions, priority calculation, maps, and hotspot analysis as later increments; keep recommendations reviewable by a human officer.
\item Improve deployment readiness with environment-specific API configuration, database migrations, and secure secret management.
\end{enumerate}

\section{Final Remarks}

The implemented system demonstrates how requirements, UML models, role-specific interfaces, API operations, and relational data can be combined to manage a civic complaint from initial submission to resident verification. The present result is a functional academic project implementation with clearly identifiable gaps for further engineering. Completing the test suite, administrator workflow, and operational deployment controls would provide the strongest next step toward a more complete service.
